## 2026-10-06 · Engine-independent code: JVM modules and parsers without StAX
- **Decision:** `:core-geo`, `:core-net`, `:core-map`, `:core-search` and `:core-routing` are Kotlin/JVM modules (`./gradlew test` without Android); only `:app` is Android (`foss` flavor, minSdk 26, provisional `applicationId` `com.qtekfun.mapas`). ## 2026-10-06 · Local storage: androidx.sqlite directly, without Room
- **Decision:** `:core-data` is a pure JVM module that uses the `SQLiteDriver` interface of androidx.sqlite 2.7.0 (Apache-2.0) with a hand-written repository (`SqlitePlacesRepository`). - **Discarded:** Room KMP (toolchain risk); plain JSON without SQLite (no queries).
- **Revert:** migrate to Room on the same schema if needed; the `PlacesRepository` interface isolates the change.

## 2026-10-07 · Multi-region rendering (branch `feat/multi-region-render`)
- **Decision:** the style is generated at runtime (`map/MultiRegionStyle.kt`) from the single-source template: one `pmtiles://file://…` source per installed region (`protomaps-<i>`, ordered by region id) and a copy of each layer with a per-region source, in layer-major order (layer 1 of all regions, then layer 2…) to preserve z-order across regions. Copy 0 with the original id, the others `<id>@<i>`. `background` only once. Without regions: no sources, only background (it no longer points to a nonexistent `none.pmtiles`). MapLibre Native (≥ 11.7, Context7) supports several `pmtiles://` and `file://` sources.
- **Overlap at borders:** opaque fills and lines repaint the same pixels (harmless). Translucent layers (`buildings` 0.5, `landuse_urban_green` 0.7, `roads_rail` 0.5; `landcover` only between z5 and z7) look denser in the overlap strip. Duplicate labels (same text and place) collide with each other and only one is placed (they do not use allow-overlap). Not mitigated further: it is not known which region "wins" without knowing the polygons; pending to be seen on the phone.
- **Cost (estimate, NOT measured):** 71 layers per source (41 line, 15 fill, 14 symbol, 1 background) → 1 + 70·N layers: 3 regions = 211, 10 = 701, 25 = 1751 (`MAX_SOURCES` cap = 25; the rest is omitted and logged). The style grows ~linearly (≈ 0.3 MB of JSON with 25). Only sources with tiles in the viewport cost per frame (normally 1–3), but the layer list and style reconciliation do grow with N, and so does style loading at startup. No dedup of earth/water: each extract contains only its polygon, so one source cannot cover the others. Options if it measures badly: a low-resolution worldwide PMTiles (z0–z5) as the single land/water source and extracts only from z6; or more than one region per extract (country/community).
- **Metric:** logcat `UMSTYLE` on each style load: `sources`, `layers`, `template_layers`, `skipped`, `json_kb`, `build_ms`, `style_load_ms` (no paths or locations). Fluidity with N regions: not measured.
- **Reload:** `refreshTilesIfChanged` compares a signature (path + size + mtime of each PMTiles) instead of the first path; when returning from "Mapas" (Maps) (`onStart`) it reloads if a region was installed, deleted or replaced. No restart needed.
- **Tests:** `MultiRegionStyleTest` (Robolectric): 0, 1, N regions, unique ids, no undefined or unused source, cap and path escaping.

## 2026-10-07 · M4: route preview (branch `feat/mvp-route-preview`)
- **Decision:** the detail card's "Ruta" (Route) opens `RoutePanel` (origin = current location, car/foot/bike profile, avoid motorways/tolls/ferries/unpaved with `RouteOptions`, distance and time, close). Without a location a notice is shown and the origin is chosen by searching or tapping the map (`MapEngine.setMapTapListener`, only while choosing). `MapEngine` gains `showRoute`/`clearRoute`/`setMapTapListener` with an empty default implementation; `MapLibreEngine` draws a `LineLayer` under the points and frames the route with bottom padding for the panel.
- **Concurrency:** each computation runs on IO, is cancelled when the profile/option/origin changes and is serialized with search through a single shared `Mutex` (a single `CoMapsCore`). A native call cannot be interrupted: the **timeout (30 s)** only stops waiting and discards the late result, and the same budget is passed to the native router; an already busy core delays the next computation. The core's `CANCELLED` is shown as a timeout.

## 2026-10-07 · Navigation robustness: chaos-proof following, foreground service and core isolated in `:core` (branch `feat/nav-robustness`)

## 2026-10-07 · Add a stop to the trip in progress (branch `feat/nav-stops-recording`, no phone)
- **Follow-up to:** "Navigation over the lock screen; station card during navigation", which discarded this item for lack of re-planning.

## 2026-10-07 · Settings backup and restore (branch `feat/settings-backup`, no phone)
- **Decision:** a versioned JSON file (`format` `ultimatemaps-settings`, `schema` 1, app version, creation time, `settings` as group to key to `{type, value}`, and `installed_regions` ids) built from an explicit whitelist (`SettingsSchema`). Only whitelisted keys are exported or restored; unknown groups and keys on import are ignored, wrong types and unacceptable values (out of range, unknown enum name, non-https URL, unknown fuel) are skipped and counted, a `schema` higher than 1, a corrupt or foreign file, or one over 1 MiB is refused before anything is written. Output order is deterministic. Export and import go through the system picker (`CreateDocument` / `OpenDocument`); an import first shows a plan (changes per group, switches that need consent, regions, skipped entries) and writes only after the owner confirms. The three keys owned by a live object (offline mode and catalog URL in `RegionsController`, the recording switch in `RecordingController`) are applied through that object; the stores that cache settings in memory (navigation, fuel, cameras) re-read after the restore, and the Settings screen rebuilds its sections.
- **Consent:** the camera acknowledgement is never exported or restored. The switches whose "on" starts a connection or needs a notice (`cameras/fixed`, `mobile_zones`, `incidents`, `v16`, `roadworks`, `fuel/enabled`) are never written as on: an "on" value is remembered in `mapas_restore_pending` and listed under the backup section as "to turn on again" while the switch is still off (and kept in a later export, so exporting twice does not lose it); an "off" value is written. The owner turns them on and accepts the notice as the first time. Regions: the ids are remembered; the Maps screen shows a card with the missing ones that the current catalog has and a button that downloads them through the normal download path (so `NetworkPolicy` and offline mode apply); nothing downloads on import.
- **Excluded on purpose (allow-list `SettingsSchema.excluded`, each with a reason):** the camera acknowledgement; the last map camera (a position); the install location (device-specific storage id); the default places list id (database row id); the native core's isolation valve (debug); the restore bookkeeping itself. Never in a preference file: searches, tracks, parked car, caches, downloads, credentials.
- **Everything file:** one ZIP made by `BackupService.write(out, extraEntries)` (new optional parameter): the unchanged places entry `mapas-backup.json` plus `mapas-settings.json`. `BackupService.restore` ignores unknown entries, so the combined file is still a valid places backup and the places format version did not change. Import of a ZIP restores places first (merge mode, nothing deleted; if that fails nothing else changes) and then the settings.
- **Guard against forgetting:** `SettingsSchemaCoverageTest` reads the key constants of every preference-backed class by reflection and fails if a key is in neither the whitelist nor the exclusion list, and lists every source file that opens a preference file so a new one cannot slip in.
- **Discarded alternatives:** dumping every preference file (would export positions and the acknowledgement); restoring the acknowledgement or the switches as accepted (the notice must be accepted by the owner on the new phone); applying the file through each store's `update` (duplicates the field mapping and loses the single whitelist); a Storage Access Framework tree grant or automatic backups (no permission, no hidden copies, the owner decides where the file goes); recreating the activity after an import (loses the result message).
- **Verified:** JVM tests (round trip through real SharedPreferences into fresh stores, determinism, unknown keys, wrong types, newer schema, corrupt files, ZIP variants, consent, coordinator flows with a fake places backup, Compose tests of the section and the Maps offer). **Not verified:** the system pickers and the real database restore on a device, how the section looks.
- **Owner decisions:** (1) whether the camera notice should be restored as accepted (today: never); (2) whether `voice_alerts` and any later preference should be added to the whitelist as they land (the coverage test forces the choice); (3) whether to offer the export from the first-run screen too.

## 2026-10-07 · Live step-by-step public-transport follower (branch `feat/transit-follow`, no phone)
- **Decision:** a pure follower in `:core-transit` (`ItineraryFollower`) driven by position fixes and an injected clock, a `TransitTripController` that owns the one trip (like `NavigationController` does for the car), a separate `TransitTripService` (foreground, type `location`), a `TransitTripHost` + `TransitTripScreen` over the map, and prompts through the navigation voice or a chime. Started by a *Start* button on the itinerary card (`transit_trip_start`; all earlier test tags are kept).
- **Why a separate controller and service instead of reusing the car navigation's:** `NavigationController`, `NavigationSession` and `NavStateStore` are built around a `RoutePlan` (a polyline with maneuvers and distance along it); a transit trip is a list of timed legs and its progress is "which stop", not "which metre". Forcing one into the other would have touched shared navigation code that other branches edit. The service is a small copy of `NavigationService` (start/resume/stop, persisted state, 3 h expiry, battery-saver throttle) and reuses its parts that are generic: `NavNotificationThrottle`, `NotificationDedupe`, `LiveUpdatePolicy`/`LiveUpdateNotification` (the chip is promoted with the same *Show distance in the status bar* switch), `KeepScreenOn`, `ShowOverLockScreen`, `NavigationTheme` (night and glove), `SharedNavUiPrefs` (the glove switch is shared), the voice queue and the Mute switch.
- **Matching rule (design choices, none measured):** a ride is the stop sequence joined by straight lines (the index has no shapes). A fix is matched to the nearest segment within `150 m + accuracy`; progress is `stop index + fraction`, only forward while fixes arrive; skipping two or more stops needs two agreeing fixes unless the signal was lost; a stop counts as reached within `50 m + accuracy` (at most 250 m); fixes worse than 200 m are ignored. Walking vs riding is told by speed: at or above **2.5 m/s** (about 9 km/h) two fixes in a row, away from the stop and on the line, mean boarded. The first choice, 4 m/s, was wrong: playing real planned itineraries from the Madrid index through the follower showed a Madrid urban bus hop timetabled at 3.2 m/s that it never recognised (the trip went off plan). That is why the test on the real index exists.
- **Underground:** after 45 s without a usable fix on a tram, metro or rail leg (GTFS route types 0, 1, 2) the progress is dead-reckoned from the timetable shifted by the last known offset and the state is `ESTIMATED` ("No GPS: position estimated from the timetable", plan chip "On plan (estimate)", prompts worded "by the timetable"). Boarding can also be estimated when the last fix was at the stop and the scheduled departure has passed; a standing fix at the stop afterwards undoes it. The estimate never completes a ride: only a real fix at the alighting stop does. A bus leg with no fix is shown as "Waiting for GPS" with the last known progress, never extrapolated.
- **"As expected" means the schedule only:** ahead/behind is the clock against the scheduled time at the matched position, shown as "About N min behind plan" (dead band 90 s: "On plan"; ahead only while riding). Connection: margin = next scheduled departure minus (projected arrival + walking time); under 60 s is *at risk*, more than 30 s negative is *missed*; waiting at the stop it is *missed* only 120 s after the scheduled departure (vehicles run late).
- **Off plan and re-plan:** off plan = the position leaves the line's corridor for 4 fixes in a row, or a walk moves 250 m further from its target than the closest it got. It recovers by itself when the position matches again. **Re-plan is only a button** (shown when off plan or a connection is missed; never automatic): `TransitService.plan` from the last known position to the same destination, leaving now, on the IO dispatcher; a failure leaves the trip as it was and says so.
- **Prompts:** `AlertSoundMode` is reused (voice, sound, silent; default **voice**) in a new setting `mapas_transit_trip/prompts` (Settings, Navigation, *Transit trip prompts*, in the backup whitelist and the coverage test). The delivery policy is `AlertDeliveryPolicy` (the navigation Mute silences everything), "only important prompts" keeps the urgent ones, the third chime (`ChimeKind.TRANSIT`, 784 then 1047 Hz, rising, a pitch that has NOT been tuned on a device) is generated in code like the other two. Sentences in Spanish and English in `TransitPhrases` (`:core-voice`, which now depends on `:core-transit`).
- **Live Update chip:** since `feat/live-update` was merged into the base meanwhile, the chip is plugged in already: "N stops" while riding, "Get off" at the next stop, "N min" while waiting for the departure, the walking distance while walking, "Re-plan" off plan; 7 characters or fewer in English (the platform's suggested maximum), "N paradas" in Spanish is a little longer.
- **Privacy:** positions stay in memory; the saved file holds the itinerary and the progress, no position; nothing is logged or sent. `PRIVACY.md` (both languages) says so.
- **Not built / limits:** no shapes (so the corridor is generous and a curvy line may fit loosely), no platform information (the index has none: "Change here" names the line and the stop only), no real time, no map camera that follows the traveller (the map shows the itinerary and the user dot only), a car navigation and a transit trip are not prevented from running together, no check that the traveller is on the *right vehicle* on a street served by several lines (only the speed and the corridor).
- **Verified (JVM and Robolectric only, nothing on a phone):** the follower on a synthetic trip (walk, wait, ride, transfer, missed connection, off plan, underground gap and recovery, arrival), whole trips played back by a simulator (also with a 2 min delay and a blackout), the same playback on itineraries planned on the real Madrid index when `~/mapas-data/transit/out/transit-madrid.umti` exists, the store (round trip, expiry, corruption), the controller and host over a simulated location source with virtual time, the screen, texts, speaker, settings and the service (resume with a null intent, expired trip, stop).
- **Owner to decide:** whether the prompts should default to the chime like the camera alerts; whether a car navigation should stop a transit trip (and the reverse); the 3 h expiry for a transit trip (copied from the car navigation); whether to publish a test build for a real ride (`docs/phase2/transit-follow-checklist.md`).
- **Discarded alternatives:** extending `NavigationController` with a transit mode; one shared notification channel and id; automatic re-planning; following without a service (the screen would have to stay on); shapes in the index for a tighter match (index size, not measured).

## 2026-10-08 · Tunnel positioning stage 1: tunnel-aware dead reckoning (code, JVM-tested only)
- **Decision:** `RouteTracker` gets a `TunnelEstimator` and an optional `TunnelSpanSource`. Where a span is known and the signal is lost before or inside it (entry margin 150 m), the estimate keeps advancing until the span exit (never past it, never to the end of the route, so no arrival inside a tunnel), with a speed model that smooths the speed over the last fixes, carries a braking or accelerating trend for 3 s and then holds the speed, and freezes while an optional `StopGoSignal` says the vehicle is stopped. Hard caps: 10 km and 10 min of estimate. `NavState` has `errorMeters` (accuracy + 0.05 m per metre + 1 m per second, bounded by the span length) and `inTunnel`; the status strip shows "GPS lost in tunnel" (en/es) instead of the generic text. Inside a span the `NOW` prompt is replaced by `NEAR` while the error is larger than the `NOW` band. A poor fix (accuracy over 30 m) within 60 m of the exit snaps to the exit.
- **No span, no change:** without a known span the old estimate (last speed held, 30 s cap) is used as before; the new fields only add the error radius. This is covered by a regression test.
- **Where the spans come from:** the CoMaps JNI route result does NOT expose tunnel information (`FillGuidance` in `um_core.cpp` emits only maneuvers, lanes and speed limits per segment) and the submodule is not buildable in this session, so the wire format was not touched. Instead: `TunnelSpanSource` (plug-in point for a later native flag or OSM data) and `LearnedTunnelStore`, an in-memory fallback that remembers a signal loss of at least 8 s and 120 m as a tunnel (entry and exit coordinates, never persisted, never logged, never sent) and gives the next route through the same place a span. Learned exits are trusted less (15% + 50 m of slack). Wired in `MapasApp`. Discarded: persisting learned tunnels (location history, needs an owner decision); parsing OSM at run time (cost unknown).
- **IMU:** only the `StopGoSignal` interface plus a scripted fake in tests; no Android sensor code (needs a drive to tune).
- **Simulated numbers** (`TunnelEstimatorTest`, virtual time): constant speed through a 2 km tunnel, worst error under 15 m; stop at the end of the tunnel, 1239 m of error without a stop/go signal against 8 m with one; braking before the tunnel, 191 m (held speed) against 64 m (trend model) after 30 s.
- **Not verified:** nothing was run on a phone or in a real tunnel; the error constants and the speed model are tuned on synthetic drives only; the learned store can mistake a long GNSS outage for a tunnel (then the dot is bounded by a wrong exit until the next fix, which wins); the UI wording was not reviewed by the owner; the `NOW` suppression and the learned store are not covered by instrumented tests. The app module compiled, its unit tests and `lintFossDebug` passed.
- **Next (needs a device):** Android `StopGoSignal` from `TYPE_LINEAR_ACCELERATION` (stage 1b), native tunnel flag per segment, owner review of the dimmed dot driven by `errorMeters`.

## 2026-10-08 · Tunnel positioning: real tunnel source from the native core (patch 0004, JVM-tested only)
- **Decision:** the CoMaps core now tells which route segments are tunnels. Patch `0004-route-tunnel-spans.patch` adds `LoadedPathSegment::m_isTunnel` (set in `DirectionsEngine::LoadPathAttributes` when the road feature has a `highway|<class>|tunnel` classificator type, i.e. OSM `tunnel=*`) and `RouteSegment::IsTunnel()/SetTunnel()`, copied to every route segment of the road. `FillGuidance` appends an optional trailing section `[nTunnels, from, to, ...]` (point indices, same convention as the speed limits) after the limits, only when the route has a tunnel, so a route without tunnels is byte-identical to before; the guidance wire version stays 1. Kotlin: `RouteGuidance.tunnels: List<TunnelRange>` (default empty), decoded by `GuidanceWire`, remapped by `RoutePlan.sanitized()`, saved by `RoutePlanCodec` (version 2; version 1 files are still read, with no tunnels).
- **Priority:** `RouteTracker` builds its spans with `PreferredTunnelSpanSource(RouteTunnelSpanSource(plan.guidance.tunnels), learned)`: engine spans first (`TunnelSource.ROUTE_FLAG`, full confidence, no slack), the `LearnedTunnelStore` only where its spans do not overlap an engine span; observations still go to the learned store.
- **Bench:** debug `CoreBenchActivity` has `--ez tunnels true`: three car routes in Madrid (Sol-Atocha, Nuevos Ministerios-Atocha, Puente de Toledo-Avenida de America through the Calle 30 tunnels) logging ranges, along-route metres and lengths (no coordinates). Not run.
- **Limits:** only roads tagged as tunnels in the map data; a long underpass tagged only `covered=yes` or a `building_passage` is not reported; a tunnel split into several OSM ways gives adjacent ranges that are merged by `sanitizeSpans`. The generator may not keep the tunnel type for every road class.
- **Not verified:** the patched native library was built (`assembleFossDebug`) but cannot run on the host; no route has been calculated with it, so it is unknown whether real Madrid routes carry tunnel ranges, how accurate their ends are, and the extra cost per route (expected negligible: one classificator walk per loaded road). To check on the Pixel 8 (needs the owner's permission): run the `tunnels` bench and compare the logged ranges with the map.

## 2026-10-08 · Tunnel motion sensors: Android StopGoSignal (stage 1b, JVM-tested only)
- **Built:** `MotionDetector` (core-nav, pure Kotlin): variance of the accelerometer magnitude over a 3 s window, hysteresis band (stop at or below 0.004, move at or above 0.02, in (m/s^2)^2), STOPPED needs 5 s of quiet and MOVING 1.5 s of noise, UNKNOWN until decided or when samples go stale. `AndroidStopGoSignal` + `SensorManagerSampleSource` (app): `TYPE_LINEAR_ACCELERATION`, else `TYPE_ACCELEROMETER`, `SENSOR_DELAY_NORMAL`, no batching. No gyroscope (not needed for the magnitude; fewer sensors, less battery).
- **Lifecycle:** the tracker only asks `motionState` during a loss inside a known span, so the first question registers the sensor; the new `StopGoSignal.release()` (default no-op) is called when a fix returns and when the session stops, which unregisters at once. Without a sensor, with the setting off, or with stale samples the answer is UNKNOWN and the estimator keeps its old behaviour. Samples live in a fixed in-memory ring and are never stored, logged or sent.
- **Setting:** "Use motion sensors in tunnels" (Settings > Navigation, default ON, key `motion_sensors_tunnels` in `mapas_nav`, in the backup schema; read live, so no restart). PRIVACY.md updated in both languages.
- **Thresholds are NOT tuned on a drive.** They are first guesses; a smooth steady cruise has little vibration and could read as STOPPED after 5 s (hence the long dwell and the UNKNOWN start). Needs the Pixel 8 in a real tunnel and a queue to tune `MotionDetectorConfig`.
- **GNSS fade trigger skipped:** it would need a `GnssStatus` callback running during the whole navigation (battery) and a new "early loss" input in `RouteTracker`, which changes the loss semantics; not cheap or safe for this step. Discarded alternative: sensors always on.

## 2026-10-08 · Cercanías real time (opt-in switch, branch `feat/cercanias-rt`, JVM and Robolectric only, no phone)
- **Decision:** Renfe's GTFS-RT delays, cancellations and alerts for Cercanías, behind **Settings, Navigation, *Cercanías real time*, OFF by default**, in `mapas_transit_trip` (`cercanias_real_time`), in the backup whitelist as a consent switch (restoring a backup never turns it on) and in the coverage test. The owner accepts the licence doubt (data.renfe.com states CC BY 4.0 on the dataset pages but no general licence) because nothing is redistributed: the phone asks Renfe's server itself.
- **Feeds (re-checked at the source on 2026-10-08):** `https://gtfsrt.renfe.com/{trip_updates,vehicle_positions,alerts}.json` (and `.pb`), no key, CC BY 4.0 on the dataset page, "every 20 seconds". The JSON has the same information as the protobuf, so there is **no protobuf code and no new library** (kotlinx.serialization is already there). Real files: ~124 KB trip updates (296 trips), ~100 KB alerts (69), ~111 KB vehicles. Numbers: 64-bit values are strings; a trip update carries a trip-level `delay` plus usually ONE stop update (the next stop, `arrival.time` and `arrival.delay`); cancelled trips have only `scheduleRelationship: CANCELED`; skipped stops are `SKIPPED`; alerts are Spanish text with `routeId`s like `10T0014C4a` (and a few `stopId`s). Vehicle positions are parsed but not fetched (the trip id already gives the delay), so one refresh is trip updates + alerts, ~225 KB.
- **Can the ids be matched? Partly, and the index needed a change.** Checked against the national `fomento_transit.zip` that the Madrid index is built from: 228 of 296 live trip ids and 346 of 346 stop ids exist in it, and for the stop updates predicted time minus delay equals the scheduled time (281 of 285 within a minute). But the **index did not keep any id** (stops and trips are bare integers), so the published Madrid index cannot be matched. Fix: `FeedOptions.keepIds` (set for the `renfe` namespace by the build CLI) keeps the stop and trip ids in an **optional trailing section** of the `UMTI` v2 file (old files still load and simply have none; a ride then has no `tripId` and shows no real time); ~13 bytes per trip. **The Madrid index must be rebuilt and republished before the feature does anything on a phone** (owner action; not done here).
- **Fallback by route, stop and time: designed, not built.** The feed has no coordinates or names, so without stop ids it cannot be tied to a stop at all; with stop ids but no trip ids a match would be (line suffix of the trip id, stop id, predicted minus delay within a minute of the scheduled time), but it cannot see cancelled trips (they carry no stop) and opposite directions at one station are ambiguous, and the same build gives both ids anyway. Not worth the code.
- **Guards:** a trip id repeats every day and the feed only describes today, so a ride is matched only if it is scheduled between 3 h before and 4 h after now AND, when the feed gives a stop update for one of its stops, the implied schedule agrees with the planned time within 10 min; otherwise the train found is another day's run and is ignored. Zero delay is a real answer ("On time"); a train missing from the feed says nothing (never "on time").
- **Network:** `HttpRealTimeFetcher`: plain GET, https only, through `NetworkPolicy` with a new purpose `TRANSIT_REALTIME` (host `gtfsrt.renfe.com` is added to the policy only while the switch is on, listed in the connection list, logged on every attempt, blocked by offline mode, removed on switch-off), no cookies, no query, `User-Agent: UltimateMaps` (the same for everyone), 8 MB cap, redirects re-authorized. `RealTimeRepository`: at most one refresh per 30 s whoever asks (failures back off 30 s, 60 s... up to 5 min), data older than 3 min is hidden, any failure is silent and keeps the old data, alerts are best effort. Refresh happens once when an itinerary with a Renfe train is shown and every 30 s while a trip is followed. With the switch off nothing is asked, not even the policy (test with a policy that fails on any call).
- **UI:** cards show "Real time (Renfe) · Delayed 4 min / On time / N min early / Cancelled", alerts ("Alert: ...", cut at 200 chars), skipped boarding/alighting stops; the list shows "C4 · Delayed 4 min"; the footer note says which legs have real time and that the rest do not; the follower shows the same as strips, the plan chip ("About 4 min behind plan") uses the train's real delay instead of the clock comparison, "Board now" and the connection margin use the real departure, a cancelled train is a missed connection (Re-plan appears), the underground estimate also shifts by the delay and does not board a cancelled train, and the note under the arrival time is "Real time (Renfe)" only for a ride found in the feed ("Scheduled times, no real-time data" otherwise). Renfe is named as source in the setting, the card footer and PRIVACY.md.
- **Discarded:** a protobuf decoder (JSON is enough); fetching per leg or per position (would reveal the trip; the national file is filtered on the phone); always-on polling; storing the data on disk.
- **Unverified on a phone / in the wild:** the whole flow (no phone was used); how the real `trip_updates` behave on Madrid lines with a rebuilt index (matching was verified only against the static file and with synthetic fixtures); whether Renfe throttles or blocks the generic user agent over time; alert relevance (matched by line name only, so a C4b alert also shows for C4b rides, not for C4).

## 2026-10-08 · Public-transport planner: walk when it pays, walking cap, mode filter (branch `feat/transit-options`, no phone)
- **Decision (owner-approved design):** (A) the walk-only itinerary is always one of the options when the straight-line walk with the detour factor takes at most `walkAlternativeMaxSec` (default 20 min). Then a vehicle journey must beat it by `max(minTransitSavingSec = 5 min, 20 % of the walk)` or it is dropped; if some journey beat the walk but not by enough, the walk comes first with the note "Walking is about as fast" (`JourneyNote`). A later "next departure" is compared with leaving on foot at the time asked. `maxTotalWalkSec` (default 15 min, 0 = no cap) drops journeys that walk more in total. (B) A request takes a set of allowed modes (`TransitMode`: bus, metro, tram, train, ferry, other) derived from the GTFS route type, basic codes and the extended ranges (100-199 and 300-399 train, 200-299 coach and 700-899 bus/trolleybus as bus, 400-499 metro, 900-999 tram, 1000-1299 ferry; the rest, such as funicular, cable car or monorail, is "other" and always allowed). Lines of an excluded mode are never boarded; walking transfers are never excluded; when nothing is left because of the filter the answer is `NoRouteWithModes` ("No route with the selected transport"). The filter also applies to the next-departures search and to the follower's re-plan.
- **UI and settings:** a compact row of mode chips above the itinerary list (only the modes the city's index has; hidden when it has fewer than two switchable modes), all on by default, with Reset when one is off; the choice is remembered. Settings > Navigation, new "Public transport planning" cards (next to the existing transit trip cards, not a new hub category, to leave the hub alone): show walking under 10/15/20/30/45 min, prefer walking if transit saves under 0/2/5/10/15 min, max walking 5/10/15/20/30 min or no limit. All four values (`plan_modes`, `plan_walk_alt_min`, `plan_min_saving_min`, `plan_max_walk_min`) are in `mapas_transit_trip`, the backup whitelist (plain, no consent) and the coverage test; strings in English and Spanish.
- **Limit of the walking cap:** RAPTOR keeps one earliest-arrival label per stop and round, so the cap is a filter on those journeys plus a limit on the access and egress walk, not a second criterion in the search: a journey that walks less but arrives later is not looked for. Raising the cap or turning it off is the escape hatch.
- **Route types in the five published indexes** (data release `data-261004-20261007-i`, read by `RealIndexModesTest` from `~/mapas-data/transit/check/`): lines by route_type to switchable chips: **Barcelona** {0 tram 5, 1 metro 14, 2 rail 33, 3 bus 1486, 7 funicular 3, 200 coach 43} gives bus (coach folded in), train, metro, tram and other (5 chips); **Bilbao** {3 bus 46, 7 funicular 1} gives one switchable mode, so the chip row is hidden; **Madrid** {0 tram 4, 2 rail 34, 3 bus 654} gives tram, train and bus (the published index has no Metro de Madrid because that feed was expired; it will show a metro chip once it is back); **Seville** {0 tram 1, 1 metro 1, 3 bus 58} gives bus, tram, metro; **Valencia** {0 tram 33, 1 metro 83} gives tram and metro. Every feed has meaningful basic route types; the only extended code is 200 (coach) in Barcelona, which the mapping handles. Madrid's source feeds checked directly: Metro 13 lines type 1, Metro Ligero 4 lines type 0, EMT 236 / interurban 354 / other urban 117 lines type 3, Cercanias (CRTM) 10 lines type 2, Renfe national 646 type 2 and 182 type 3. No extended 100-1700 codes appear in any Madrid feed.
- **Discarded:** a new Settings hub category (shared file, more risk); stored seconds (minutes are what the controls show); making the walk cap exact with a second RAPTOR criterion (index and query cost); seeding the search with the required saving (the note then could not be known).
- **Unverified:** anything on a phone; how the chips look on a small screen; real-data route quality with the new thresholds (JVM tests on made-up feeds only).

## 2026-10-08 · The route preview frames the whole route, origin included
- **Decision:** a pure fit (`core-map` `RouteCameraFit`: Web-Mercator, 512 px tiles) computes the flat north-up camera that puts every route point in the screen minus what covers the map; `RoutePadding` (status bar, top bar, right button column, bottom sheet at its current detent) feeds it; `RouteFraming` decides when. ## 2026-10-08 · The vehicle marker glides: one pose per display frame instead of one per fix (branch `fix/nav-puck-smooth`, no phone)
- **Report:** during navigation the vehicle icon moved in jerks.
- **Cause:** the marker (a GeoJSON point plus the arrow layer) was rewritten once per fix, so about once per second, with no interpolation, while the camera followed on its own timeline: `NavCamera` throttled to 800 ms and sent an `animateCamera` of 880 ms toward each fix, and each new one cancelled the previous. The marker stepped on the map and, as the camera glided independently, also against the screen. Nothing was wrong in `RouteTracker` (the matched position is the projection on the polyline, exact) or in `NavSimulation` (1 Hz fixes by design).
- **Decision:** `PuckInterpolator` (pure, no allocation, virtual-clock tests) turns the 1 Hz fixes into a pose per frame. In metres along the route polyline the displayed point chases a prediction (last fix plus last speed times the time since the fix, for at most 1.5 s, never past the route end) at the last speed plus a correction with a 400 ms time constant; it slides back at most 2 m/s, catches up at most `3 * speed + 5` m/s, and resyncs at once after a reroute, a mode change or an error above 150 m. Off the route it applies the same law along the course. The heading eases by the shortest angle (250 ms) and is kept below 1 m/s. `NavPoseDriver` pushes marker and camera in the same display frame (`Choreographer`, started by `NavHost` only while something can change): the camera centre IS the marker plus an offset that decays to zero; zoom, tilt, bearing and padding ease toward the `NavCameraPlanner` target (250 ms, or 350 ms for a start, recenter or 2D/3D switch, about 1.2 s). `NavCamera.next` (throttle) is no longer used by the host.
- **Frame rate and battery:** at most 60 pushes per second (every second frame on a 120 Hz display), 30 in battery saver (checked every 5 s). A standing car pushes nothing and the loop stops; nothing runs with the activity stopped (screen off) or when navigation is not active; the loop restarts with the next fix. The maths allocates nothing; the small objects handed to the MapLibre API (point, camera position) are the map library's interface.
- **Reason:** a single source of motion for the marker and the camera removes both the steps and the mismatch. **Discarded:** `LocationComponent` (its own location engine and puck rendering, no route-aware interpolation, and it would add a second pipeline); animating only the marker with a `ValueAnimator` per fix (the camera would still fight it); lengthening the camera animation (does not move the marker).
- **Unverified on a phone:** how smooth it looks on the Pixel 8 at 60/120 Hz, the cost of 60 `GeoJsonSource.setGeoJson` per second (if it shows in frame time, lower `PowerSavePolicy.NORMAL_FPS`), and the battery saver cap.
